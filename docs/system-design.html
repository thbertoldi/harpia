executive view

Visão Geral

Harpia é uma plataforma operacional multi-tenant e agentic. O usuário não cria tarefas soltas: ele conversa com uma assistant de configuração que seleciona e parametriza planos reutilizáveis.

Produto

Chat-first PlanConfiguration assistant. A UI é navegador sobre threads, execuções e artifact stream.

Execução

Temporal coordena durabilidade, retries, sinais humanos e StepExecutions; LangGraph fica no raciocínio agentic.

Isolamento

Tenant é resolvido no interceptor, propagado para RLS, clients internos e object-store/cache wrappers.

go

Control Plane

O binário Go tem dois modos: API HTTP/ConnectRPC e worker Temporal. A camada de domínio é pragmaticamente organizada por packages internos com handlers, repositories e adapters.

API mode

cmd/api/main.go carrega config, conecta Postgres, semeia catálogo/dev data, cria handlers, instala interceptors de identidade/rate limit e registra serviços ConnectRPC.

Worker mode

HARPIA_ROLE=worker inicializa repositories, Garage, executor runtime e registra workflows/activities no Temporal task queue.

Fluxos End-to-End

Os fluxos abaixo conectam UI, contracts, control-plane, Temporal, agent-runtime e storage.

1. Conversa → PlanConfiguration

  1. Usuário envia mensagem em /new ou /chat/:threadId.
  2. ThreadService.ProposePlan usa PlanClassifier contra summaries do catálogo.
  3. Thread recebe PLAN_PROPOSED com candidatos e defaults.
  4. Ao confirmar, CreatePlanConfiguration persiste configuração DRAFT.
  5. planassistant.Controller.SeedThread emite CONFIGURATION_STARTED e primeiro ASSISTANT_PROMPT.
  6. Usuário escolhe executors, overseers e policies até virar RUNNABLE/SCHEDULED.

2. Run now / schedule → PlanExecution

  1. CreatePlanExecution valida bindings e seed readiness.
  2. Control-plane cria snapshot de config/template/installations.
  3. Temporal inicia PlanWorkflow.
  4. Workflow ordena o DAG topologicamente e cria StepExecution.
  5. Step chama RunIntegrationActivity ou RunAgentActivity.
  6. Output artifact é persistido; chat recebe eventos de progresso.

3. Human-in-the-loop

  1. Policy pode exigir approval antes de publicação.
  2. Workflow cria plan_approval_requests e aguarda signal plan-approval-decision.
  3. Agente pode retornar elicitation_requested.
  4. Runtime persiste elicitation, UI mostra Inbox/card e resposta volta como signal plan-elicitation-response.
  5. Timeout segue PlanBehaviorPolicies.

4. Artifact browsing

  1. Executor cria artifact via CreateArtifactWithPayload.
  2. Payload vai para Garage com path tenant-scoped; metadata/version vai para Postgres.
  3. Frontend chama PreviewArtifact ou GetArtifactPayload.
  4. Artifacts aparecem no thread, execution detail e browser /artifacts.

Padrões de Design

O código mistura DDD pragmático, ports/adapters e workflow orchestration. A maior parte das fronteiras está em interfaces pequenas e contratos protobuf.

Repository pattern

Packages Go expõem repositories por aggregate/capability com SQL explícito e pgxpool.

Ports & adapters

PayloadStore, PlanRuntimeStore, LLMProvider, ExecutorCatalog, PlanClassifier.

Workflow orchestration

Temporal é o orchestrator técnico de longa duração; domínio evita orquestrador agentic.

State machine

planassistant.DeriveState e status de config/execution/step controlam a jornada.

Registry/strategy

Executor registry, integration handlers, agent manifest registry e LLM provider registry.

Decorator

BudgetedLLMRegistry envolve provider calls com reserve/record usage.

Generated contract boundary

Go, Python e TypeScript consomem stubs gerados; evita serialização manual fora das bordas.

Tenant-safe wrappers

Object store/cache são encapsulados para impedir chaves globais sem tenant.

Anti-corruption layer

Planejada para Slack/human interaction; hoje aparece em adapters de integração e external providers.

Gaps e Riscos Observados

Itens úteis para orientar próximas discussões arquiteturais. Não são necessariamente bugs; vários são estágios naturais de pré-v1.

Agent runtime fallback ainda é simulado

graph.py tem worker genérico simulado; execução real está nos manifest-backed agents.

Match/list agent types incompleto no runtime

AgentServiceImpl.ListAgentTypes e MatchAgent ainda retornam vazios em partes do fluxo.

Streaming LLM limitado

Providers Python implementam stream como wrapper de complete em alguns adapters.

OpenSpec com smoke checks pendentes

Há mudanças ativas com verificação manual/live smoke ainda não concluída.

Boa fronteira de contratos

Proto + Buf e generated clients reduzem drift entre frontend, Go e Python.

Boa proteção multi-tenant

RLS, interceptors e clients internos com X-Tenant-ID deixam tenant no caminho crítico.
