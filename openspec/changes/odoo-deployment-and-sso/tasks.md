## 1. Odoo image and hardened authentication addon

- [ ] 1.1 Create `deploy/odoo/Containerfile` to extend the official Odoo 19 Community image. Fetch `OCA/server-auth` at an audited immutable Odoo-19-compatible commit (record repository URL and full commit SHA in the file), install `auth_oidc` and its declared Python dependencies during the image build, copy first-party addons from `deploy/odoo/addons/`, and configure only immutable/read-only addon directories. Do not use a floating branch, a runtime git clone, or an Odoo Online image.
- [ ] 1.2 Create `deploy/odoo/addons/harpia_auth_zitadel/__manifest__.py`, `__init__.py`, and the module implementation under `deploy/odoo/addons/harpia_auth_zitadel/`. Make it depend on OCA `auth_oidc` and enforce its OIDC authentication extension point: require the `email_verified` claim to be true; resolve only a pre-existing Odoo user through the OIDC identity linkage; reject unknown identities before a user/link can be created; and never fall back to unverified email matching. Keep Harpia connector code, bearer-token handling, and business modules out of the addon.
- [ ] 1.3 Add focused Odoo tests under `deploy/odoo/addons/harpia_auth_zitadel/tests/` for a linked verified identity (accepted), an unknown subject (rejected with no user/link creation), a false or absent `email_verified` claim (rejected), and an unverified-email-only match (rejected). Use the pinned `auth_oidc` module's supported test/authentication seam; do not mock away the hardening extension point.
- [ ] 1.4 Add `deploy/odoo/addons/harpia_auth_zitadel/i18n/harpia_auth_zitadel.pot` and `deploy/odoo/addons/harpia_auth_zitadel/i18n/pt_BR.po`. Extract all operator-visible login-denial messages, retain English source strings, and provide Brazilian Portuguese translations.

**Verification:** `docker build -f deploy/odoo/Containerfile -t harpia-odoo:dev .`; start the image with a disposable PostgreSQL 16 database and run `odoo --test-enable -i auth_oidc,harpia_auth_zitadel --stop-after-init`; confirm all addon tests pass.

## 2. Standalone Helm chart with isolated Odoo storage

- [ ] 2.1 Create `deploy/odoo/Chart.yaml`, `README.md`, `values.yaml`, `values-dev.yaml`, and `values-prod.yaml`. Define Odoo 19 image/ref, `odoo` namespace, single-replica storage policy, Odoo database/admin-password Secret references, Odoo-only PostgreSQL image/database/credentials Secret references, filestore storage, resources, and required ingress/OIDC settings. Document every pre-created Secret and make clear that the chart is an optional release independent of `deploy/harpia/`.
- [ ] 2.2 Create `deploy/odoo/templates/_helpers.tpl` with release-prefixed names and common labels; create `deploy/odoo/templates/namespace.yaml` so the chart installs resources in `odoo` by default while supporting an operator-selected existing namespace.
- [ ] 2.3 Create `deploy/odoo/templates/postgres.yaml` for an Odoo-only PostgreSQL 16 Deployment, ClusterIP Service, credentials Secret reference, and dedicated `ReadWriteOnce` PVC. Create only the configured Odoo database; do not create Harpia or Zitadel databases and do not reference their Secret names or Service names.
- [ ] 2.4 Create `deploy/odoo/templates/odoo.yaml` for the Odoo Deployment, ClusterIP Service, configuration ConfigMap, readiness/liveness probes, Odoo database/admin-password Secret references, and an Odoo filestore `ReadWriteOnce` PVC mounted at the Odoo filestore path. Use `Recreate` semantics and one replica while the filestore is RWO. Configure Odoo to load `auth_oidc` and `harpia_auth_zitadel` from the image-only addon paths.
- [ ] 2.5 Create `deploy/odoo/templates/ingress.yaml` for a `networking.k8s.io/v1` Ingress with `ingressClassName: traefik`, the configured Odoo host, a required `spec.tls` Secret, and a route only to the ClusterIP Odoo web Service. Add Helm `values.schema.json` validation (or template `fail` guards) in `deploy/odoo/` so production-oriented values fail when the host or TLS Secret is missing; never render a public HTTP fallback.
- [ ] 2.6 Add `deploy/odoo/templates/tests/` Helm test Pod(s) that assert the Odoo Service and dedicated PostgreSQL Service resolve in the Odoo namespace. Do not test via a Harpia Service or PostgreSQL endpoint.

**Verification:** `helm lint deploy/odoo/`; `helm template odoo deploy/odoo/ -f deploy/odoo/values-dev.yaml > /dev/null`; `helm template odoo deploy/odoo/ -f deploy/odoo/values-prod.yaml > /dev/null`; verify rendered resources use only the `odoo` namespace and the Ingress contains Traefik class plus TLS; `mise run helm-lint`.

## 3. Zitadel OIDC client bootstrap and Odoo configuration

- [ ] 3.1 Create `deploy/odoo/templates/zitadel-oidc-client.yaml` as an idempotent Helm bootstrap Job (with narrowly scoped ServiceAccount/RBAC only for the Odoo non-secret metadata ConfigMap). Read an operator-provided Odoo-scoped Zitadel management credential from a referenced Secret only in this Job, wait for OIDC discovery, and create or reconcile an Odoo-specific authorization-code client using the chart's issuer, Odoo redirect URI, and post-logout URI values. Do not read, write, or mount `harpia-oidc-config`, Harpia client IDs, Harpia tokens, or Harpia sessions.
- [ ] 3.2 Have the bootstrap Job publish the non-secret Odoo client ID, issuer, and configured provider metadata to an Odoo-named ConfigMap. Ensure the Odoo Deployment cannot read the Zitadel management credential.
- [ ] 3.3 Add bootstrap tests/scripts under `deploy/odoo/tests/` that use a mock Zitadel Management API or an isolated test tenant to prove first-run creation and repeated-run reconciliation. Assert a distinct Odoo client ID, exact Odoo redirect/logout URLs, and no mutation to `harpia-oidc-config`.
- [ ] 3.4 Document in `deploy/odoo/README.md` how an operator creates the Odoo-scoped management-credential Secret, configures Odoo URLs/TLS Secret, and pre-provisions a matching Odoo user. State that this does not implement the future Zitadel → Harpia → Odoo provisioning workflow and that no JIT login is available.

**Verification:** run the test harness in `deploy/odoo/tests/`; install the chart twice against a test Zitadel instance and confirm the second run reconciles the Odoo client without changing Harpia's client/config; inspect the Odoo Deployment spec to confirm the management Secret is absent.

Repeat with an unknown subject, missing `email_verified`, and `email_verified=false`; verify each is denied and creates no Odoo user/linkage. Verify the Harpia login remains usable with its original client/session after Odoo bootstrap.

**Verification:** `mise run helm-lint`; `helm lint deploy/odoo/`; `helm template odoo deploy/odoo/ -f deploy/odoo/values-prod.yaml > /dev/null`; `mise run dev` (Harpia-only regression); run the focused image/addon and OIDC bootstrap tests from tasks 1 and 3; record any frontend type-check result separately if frontend files are changed (the documented baseline is 12 errors).
